# 技术塔视觉伴侣

这是独立的 UI 设计 skill，不是六步工程流水线的一个快捷入口。目标是在浏览器里完成视觉探索、方案比较、页面迭代和设计交付；默认不写业务代码、不建 git 仓库、不生成 Tickets，也不自动进入 plan/build/review/pr。

详细的服务器、页面片段、交互事件和快照操作见 `visual-companion/GUIDE.md`。

## 模式边界

- 用户明确说「用视觉伴侣」「只做 UI」「先出设计」时，直接进入本 skill；这已构成启用本地视觉伴侣的同意，只需说明会打开本地 URL 并可能增加 token 消耗，无需再次等待确认。
- 因普通 UI 设计请求被隐式触发时，启动浏览器前先用一条独立消息征得同意，并说明本地 URL 与额外 token 消耗。
- 用户同时要求实现代码时，先确认本轮是只交付设计还是走完整工程流；若意图已明确为实现，改用 `zflow`。
- 设计完成后若用户追加实现请求，先交付设计产物，再切换到 `zflow`；不得无提示地跨入执行阶段。

## UI 设计闭环

1. **读取上下文**：只读检查现有页面、品牌素材、设计系统、目标设备与内容；没有项目时基于用户描述工作。
2. **确认设计任务**：一次只问一个关键问题，优先确认目标用户、核心任务、页面范围、平台和视觉约束。可安全推断的内容直接列为假设，不机械追问。
3. **启动视觉伴侣**：

   ```bash
   visual-companion/scripts/start-server.sh --project-dir <项目根> --open
   ```

   保存返回的完整 URL、`screen_dir` 和 `state_dir`。URL 必须保留 `?key=…`。
4. **探索方向**：先展示 2–3 个有实质差异的方向并说明推荐项。布局问题用线框，视觉风格问题用高保真稿；使用贴近真实场景的内容。
5. **逐屏迭代**：每个视觉问题使用新的语义化 HTML 文件；每轮读取 `state/events` 并结合用户文字反馈。终端文字是主反馈，点击记录是辅助证据。
6. **补齐状态**：按任务需要覆盖关键页面、空/载入/错误/完成状态、交互反馈和响应式变化。不要为了“完整”虚构不在范围内的页面。
7. **设计交付**：用户批准后，在会话目录写入 `design-spec.md`，至少记录：设计目标、已批准页面与方向、布局/组件规则、颜色与字体、交互状态、响应式规则、原型文件链接、尚未决定的问题。
8. **可选快照**：仅在用户同意并获知存放路径后，为关键页面生成 PNG；页面主体用 `data-tt-screen` 包裹。
9. **停止服务器**：

   ```bash
   visual-companion/scripts/stop-server.sh <会话目录>
   ```

   项目会话保留在 `.tech-tower/brainstorm/<session-id>/`。该路径沿用视觉引擎的兼容约定；它不表示用户已进入工程流水线。

## 完成标准

只有在用户批准设计方向，原型文件与 `design-spec.md` 均已落盘，并报告可回看的会话目录后，才算 UI 设计完成。若用户只要探索而不要求定稿，可按其要求停在概念稿，但要明确哪些内容尚未批准。

全程使用用户当前语言；没有明确要求时使用中文。
