# intake 产物：ticket_context.md

`ticket_context.md` 是任务首次启动时 Agent 已获得信息的持久化快照，存放在：

```text
.scratch/<slug>/ticket_context.md
```

它回答的是「这个 Ticket 一开始带着什么信息进入工作流」，不是需求设计文档，也不是会持续膨胀的过程日志。

## 写入时机

1. workflow 启动后，在 intake 的第一次只读检查中确定 `<slug>`。
2. 任何需求追问之前，创建 `.scratch/<slug>/ticket_context.md`。
3. 向用户展示简短摘要；用户纠正后可以修订事实错误，并记录修订来源。
4. 用户确认快照后，将其视为只读基线。后续发现、决策和验收标准写入 `spec.md`，不要回填并改写初始上下文。

如果任务恢复时文件已存在，先读取并沿用，不得根据当前对话重新生成覆盖。确需补录时只追加带日期和来源的「勘误」，保留原始内容。

## 必须记录

按实际可见信息填写；不知道就写「未提供」，不得猜测。

```markdown
# Ticket Context

## 启动信息
- 启动时间：<ISO 8601，含时区>
- Ticket 标识：<slug>
- 工作目录：<任务启动时 cwd>
- 工作区根：<启动时可见的 workspace roots>

## 用户原始请求
<保留语义与关键措辞；短请求可原文记录，长请求做忠实摘要并附来源>

## 用户提供的材料
- <附件、文件、URL、截图、外部工单编号；没有则写“未提供”>

## 初始项目状态
- 代码库/项目类型：<启动时已知>
- 相关目录或模块：<启动时已知>
- Git 状态：<仓库、分支、工作区是否有既有改动；未检查则明确写未检查>
- 已知运行环境：<仅记录与任务相关的系统、运行时、框架信息>

## 明示约束
- <用户在启动消息中明确给出的范围、技术、行为和交付约束>

## 已知事实与来源
- <事实> — 来源：<用户消息/附件/文件路径/命令输出>

## 启动时未知项
- <当时缺失、需要 intake 后续澄清的信息>

## 勘误
- 无
```

## 信息边界

- 只记录任务启动时对 Agent 可见且与任务有关的信息，包括用户首条请求、用户点名材料、环境上下文和第一次只读项目检查结果。
- 不抄录 system/developer 指令、隐藏提示词、认证信息、会话密钥、环境变量值或其他秘密。
- 不把推断写成事实；推断应留给 intake 对话或后续 `spec.md`。
- 不记录后续方案选择、范围协商、实现计划、代码变更和验证结果。
- 文件用于防止长流程或上下文压缩后遗失初始意图；发生冲突时，明确记录用户后续变更，不静默改写历史。

## 完成门槛

intake 只有在以下条件同时满足时才能进入 brainstorm：

- `.scratch/<slug>/ticket_context.md` 真实存在；
- 必填章节齐全，未知信息已明确标注；
- 用户已确认摘要，或用户明确选择「全部默认」接受当前快照；
- 问题、影响范围和下一阶段所需的关键上下文已经清楚。
